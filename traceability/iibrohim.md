# Traceability: iibrohim

**Feature:** Actionable context-overflow error messages. When a conversation is too long for the model, the CLI and the TUI show the same plain-language message explaining what happened and what to do next, instead of a raw provider error. Related: opencode compacts the conversation automatically before it reaches the model's limit.

**Property tests:** [`packages/opencode/test/session/context-overflow.property.test.ts`](../packages/opencode/test/session/context-overflow.property.test.ts)

Interview notes (C-, S-, O- lines) are in my Project 4A workbook.

## Requirement changes

| ID | Original (P4A) | Revised (P4B) | Why it changed |
|----|----|----|----|
| R5 (Step 1) | Before sending a prompt that would come close to the model's context limit, the user is warned. (At 90% of a 10,000-token limit, a warning is shown; at 50%, none.) | Once reported token usage reaches the usable context, opencode flags the conversation for automatic compaction before the next prompt; below that it is never flagged. | **Not feasible as stated.** opencode can't know a prompt's size in tokens before sending it: each provider uses its own tokenizer, and tool output added during the turn is unknown in advance. The only reliable count is the usage the provider reports after a turn. The 90% threshold was also my own number, not something interviewees asked for. What users actually needed was not to be stopped halfway through a task (C-5, O-3, S-5), and opencode already meets that need by compacting automatically once reported usage reaches the usable context. The context percentage in the TUI sidebar still gives users the early visibility C-4 and O-2 asked for. |
| R5 (Step 3) | (Step 1 wording above) | Adds: if the usable context is unknown or zero, the conversation is never flagged, and a real overflow falls back to the R1–R3 message. | **Requirement problem found by a property.** fast-check found a model with a 1-token context and no output limit. opencode reserves 32,000 tokens for the reply, so the usable context is 0, and every turn, even an empty one, counts as "reached". Taken literally, the Step 1 wording would compact every turn and stop the user, which is the opposite of what they asked for. The requirement now says what happens in that case, and the code was fixed to match (see triage log). |

R1–R4 are kept as written: each is feasible with the current error formatters, and their acceptance criteria are concrete enough to test.

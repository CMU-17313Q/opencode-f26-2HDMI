# Traceability: delshark

**Feature:** The **Copy involvement summary** button in the Review panel of the OpenCode web app. One click copies a Markdown report of what the AI changed in the session: each file, whether it was added, deleted or modified, its +/- line counts, and the changed line ranges.

**Code under test:** [`packages/session-ui/src/components/session-involvement.ts`](../packages/session-ui/src/components/session-involvement.ts) builds the copied text (`toSessionInvolvementRows` then `toSessionInvolvementMarkdown`); [`packages/app/src/utils/involvement-clipboard.ts`](../packages/app/src/utils/involvement-clipboard.ts) writes it to the clipboard.

**Property tests:** [`packages/session-ui/src/components/session-involvement.property.test.ts`](../packages/session-ui/src/components/session-involvement.property.test.ts)

Interview notes (C-, S-, O- lines) are in my Project 4A workbook.

**Requirements without a property in P4B.** R2: at this layer the +/- counts are passed straight through from the diff the server sends, so a property here would only check that a number is copied unchanged; the counting itself happens in the server's diff code. R4, R6 and R8: the clipboard and download code lives in the `app` package. R4 and R8 are already checked by example tests in `packages/app/src/utils/involvement-clipboard.test.ts` ("writes the exact markdown report and reports success", "reports failure instead of throwing when the browser denies clipboard access", "reports failure when the Clipboard API is unavailable") and by the e2e test `packages/app/e2e/user-story/involvement-copy.spec.ts`. I plan to cover R4, R6 and R8 with properties in the next project.

**AI assistance:** The property tests and generators were drafted with an AI coding assistant. I reviewed each one against its requirement and my interview notes, and I triaged every failure below.

## Requirement changes

| ID | Original (P4A) | Revised (P4B) | Why it changed |
|----|----|----|----|
| R4 | The text placed on the clipboard is exactly the summary shown, and copying again with no new changes gives identical text. | The copy button hands exactly the generated summary text to the clipboard, and generating the summary twice from the same session gives identical text. | **Can't be checked as written.** An automated test cannot read the real system clipboard (browsers block it without user permission, and unit tests have no system clipboard). What users needed was to get the same text they saw, every time (S-11, C-7, O-7). That is checkable at the point where opencode hands the text to the clipboard. |
| R6 | Copy and Download produce the same summary content for the same session. | Copy and Download receive the same generated summary text for the same session, and neither one changes it. | **Not feasible to check as written, and a conflict.** Comparing against the downloaded file needs the browser's file-download feature, which doesn't exist in unit tests. The interviewees also disagreed: staff said the download's formatting may differ (S-14), while the classmate said the two should never differ (C-9). Both agreed the content must match. Requiring both buttons to pass along the identical generated text satisfies both and is checkable. |
| R7 | The copied text is the same regardless of operating system or app language, and it uses plain newline line breaks so it pastes cleanly. | The copied text never contains `\r`, and it is identical whether the session's diffs use Windows (`\r\n`) or Unix (`\n`) line endings. | **Can't be checked as written.** A test cannot switch the operating system it runs on. The summary is built from fixed English text, so the app language never reaches it; the only operating-system difference that can reach it is Windows line endings inside the diffs. The revised wording checks exactly that, which is what users meant by "the text should always be the same" (S-14, C-10). |
| R8 | If copying fails, the user is told immediately and is never shown a success message. | When the clipboard write fails for any reason, or the clipboard is unavailable, copying reports failure and never reports success; it reports success only when the write succeeds. The Review panel shows the matching toast. | **Hard to check as written.** "Told immediately" is not measurable, and toasts can only be checked in a full browser test. What users needed was to never be misled into thinking a copy worked (S-7, C-4). The revised wording names the observable result (the copy reports failure, never success) and which toast appears. |

R1, R2, R3 and R5 are kept as written: each is feasible with the current code, and its acceptance criteria are concrete enough to test.
